EmployeeBankRestApi - Deployment Guide
1. Purpose

This document describes the procedure for building, deploying, starting, verifying, and rolling back the EmployeeBankRestApi Spring Boot application.

The application provides REST APIs for:

Employee management
Bank account management
Deposit operations
Withdrawal operations
Account balance inquiry

The application uses Microsoft SQL Server for persistent data storage.

5. Verify Java Installation

Check the installed Java version:

The project uses Java 21.

Expected output should indicate Java 21, for example:

Also verify Maven:

mvn -version

Maven should show Java 21 as the Java runtime used by Maven.

6. Database Configuration

The application uses Microsoft SQL Server.

The database connection is configured in:

src/main/resources/application.yml

The datasource configuration contains the SQL Server JDBC URL, driver configuration, and connection properties.

Example structure:

spring:
  datasource:
    url: jdbc:sqlserver://<SERVER>\<INSTANCE>;databaseName=<DATABASE>;integratedSecurity=true;encrypt=true;trustServerCertificate=true
    driver-class-name: com.microsoft.sqlserver.jdbc.SQLServerDriver

The actual server, instance, and database name must match the deployment environment.

For environments using Windows Integrated Authentication, the required Microsoft SQL Server authentication configuration must also be available on the deployment machine.

Sensitive credentials and secrets must not be committed to source control.

16. Account Business Rule Verification

The withdrawal operation must verify that the account has sufficient balance.

Example:

Current Balance = 5,000
Withdrawal       = 7,000

The withdrawal must be rejected.

Expected response:

400 Bad Request

with an appropriate message such as:

Insufficient balance.

This verifies that the account business logic is working correctly after deployment.

20. Stop the Application

If the application is running directly in the terminal, stop it using:

21. Deployment Failure

If the application fails during startup:

Stop the failed application instance.
Review the Spring Boot console logs.
Verify Java 21.
Verify Maven build.
Verify SQL Server availability.
Verify the database connection.
Verify application.yml.
Verify the SQL Server JDBC driver.
Verify port 8089.
Correct the issue.
Restart the application.
Run the Postman verification again.
22. Common Deployment Problems
22.1 Port Already in Use

Check port 8089:

netstat -ano | findstr :8089

If another application is using the port, stop the process if appropriate or configure another available port.

22.2 SQL Server Connection Failure

Check the following:

SQL Server service
SQL Server instance
Database name
JDBC URL
SQL Server JDBC driver
Integrated authentication configuration
Firewall/network connectivity

The application must be able to establish a JDBC connection before Employee and Account APIs can access the database.

22.3 Integrated Authentication Failure

If the application uses:

integratedSecurity=true

verify that the required SQL Server JDBC authentication support is correctly installed and available to the JVM.

The SQL Server JDBC driver must also be present in the Maven dependencies.

22.4 JAR Does Not Start

Check Java:

java -version

Check the generated JAR:

target/

Then execute:

java -jar target/<generated-jar-name>.jar

Review the console output for the root exception.

22.5 Database Connection Timeout

23. Rollback Procedure

If the newly deployed version causes problems, restore the last known working version.

Example deployment structure:

deployment/
|
+-- current/
|   +-- employee-api.jar
|
+-- backup/
    +-- employee-api-previous.jar

Rollback procedure:

1. Stop current application
        |
        v
2. Preserve application logs
        |
        v
3. Remove or rename faulty JAR
        |
        v
4. Restore previous working JAR
        |
        v
5. Start previous version
        |
        v
6. Verify SQL Server connection
        |
        v
7. Verify Employee APIs
        |
        v
8. Verify Account APIs
        |
        v
9. Run Postman tests
        |
        v
10. Record rollback
24. Database Rollback Consideration

Application rollback and database rollback are separate operations.

Before making database schema or data changes:

Take an appropriate database backup.
Document the database change.
Verify the change against the application version.
Maintain compatibility between the application and database schema.

Do not manually delete production data as part of an application rollback.
